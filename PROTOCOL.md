# Local canvas connection protocol v2

One daemon represents one main task and up to 64 delegated workers. It binds a random TCP port on `127.0.0.1`, an exact SceneMint origin, a main workspace, a UUID session ID, and an Agent ID `scenemint-cli:<main session UUID>`. Delegates have distinct session credentials/workspaces while sharing that Agent identity and its undo stack. The connection is deliberately independent of Electron and host-specific Agent runtimes. HTTP route names retain `/v1/`; the mandatory `protocolVersion:2` handshake selects the incompatible role-aware wire contract.

Every HTTP request must have the exact `Host: 127.0.0.1:<port>`. JSON bodies are at most 36 MiB and must be plain JSON objects. Prototype-related keys are rejected recursively. No evaluation, arbitrary URL fetching, or arbitrary method dispatch is supported.

## Browser routes

All browser routes require the exact configured `Origin` and use POST with JSON. Except `/v1/pair`, they require `Authorization: Bearer <browserToken>`. A CLI token cannot authorize browser routes. Responses include the exact allowed Origin, never `*`.

OPTIONS allows POST with Content-Type/Authorization. An approved-origin preflight requesting private-network access receives `Access-Control-Allow-Private-Network: true`. Browser local-network policy still applies.

| Route            | Request                                                            | Response                                                                |
| ---------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| `/v1/pair`       | `{protocolVersion:2,code,canvasId,projectId}`                      | `{protocolVersion:2,browserToken,agentId,agentName,canvasId,projectId}` |
| `/v1/next`       | `{}`                                                               | `{requestId,method,params,turnId,role:"main"                            | "worker"}`or`{idle:true}` after at most 20 seconds |
| `/v1/reply`      | `{requestId,result}` **or** `{requestId,error:{code,message,...}}` | `{ok:true}`                                                             |
| `/v1/disconnect` | `{}`                                                               | `{ok:true,disconnected:true}`                                           |

The pairing code has 256 random bits, expires after ten minutes, and can be consumed once. Successful pairing fixes canvas/project for the lifetime of the session. The browser registers the supplied identity and injects it, the paired canvas, and request turn IDs into the semantic bridge. The browser decides the user-approved scope and checks the current canvas role for every relevant operation.

Both sides reject missing or incompatible protocol versions with `protocol_mismatch`; an old page may not silently treat a worker as main. Every browser request dispatch requires the daemon-authenticated role, with no default for a missing role. `src/policy.mjs` is the shared Node-free policy used by both the daemon and browser before forwarding a command to the existing semantic bridge.

`next` has at most one outstanding poll per session. The browser should dispatch calls without blocking its polling loop, keeping a poll outstanding or making a new request promptly while expensive operations run. The polling loop supplies liveness: 45 seconds without browser contact moves the session to `reconnecting` (it does **not** end it). Version 0.5 makes the daemon the sole authority on whether a session is alive. The page writes its browser credential to tab-scoped sessionStorage as soon as it is paired (and again whenever the daemon rotates it), keyed by endpoint and scoped to project/canvas with a ten-minute local expiry; `/v1/suspend` on pagehide is a courtesy that starts the recovery window early, not a requirement. Any later mount of the same canvas in that tab — reload, address-bar navigation, in-app navigation, bfcache — offers the credential back through `/v1/resume`, and a live page whose poll fails keeps retrying `resume` with backoff until the daemon answers. The credential is never placed in localStorage, URLs, CLI output or account storage. Only an explicit browser disconnect, a CLI stop, a changed scope, or an expired recovery window ends a session.

## CLI routes

CLI routes require `Authorization: Bearer <cliToken>` and reject **any** Origin header. A browser token cannot authorize them. Long-lived CLI credentials are stored only in a private per-session file; they are not printed or passed in process arguments.

| Route               | Request                                          | Response                                                                                                                                                     |
| ------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /v1/status`    | none                                             | `{ok,sessionId,endpoint,daemonPid,state,connected,pageAway,queuedCommands,pageLastSeenAt,agentId,agentName,origin,workspace,canvasId,projectId,pending,...}` |
| `POST /v1/call`     | `{requestId,method,params,turnId,wait?,waitMs?}` | The page's business result, without another envelope; `page_away` while the page is absent (see Reconnect)                                                   |
| `POST /v1/stop`     | `{}`                                             | Main stops the daemon/all delegates; worker revokes only itself                                                                                              |
| `POST /v1/delegate` | `{name,workspace}`                               | Main only: new public worker session information; token is saved privately                                                                                   |
| `POST /v1/revoke`   | `{sessionId}`                                    | Main only: `{ok:true,revoked:true,sessionId,deliveredRequests,alreadyRevoked}`                                                                               |

The main allowlist is `list_canvases`, `snapshot`, `health`, `ls`, `read`, `resources`, `model_catalog`, `grep`, `tasks`, `apply`, `run_node`, `cancel_node`, `undo`, `redo`, `operations`, `changes`, `timeline`, `end_turn`, `media_info`, and `media_chunk`. All `params` are objects. Scope/identity fields `role`, `actor`, `scope`, `canvasId`, `projectId`, `agentId`, `turnId`, `sessionId`, and `parentSessionId` are forbidden in `params` (the one exception is `tasks.scope`, a three-value listing range, validated as such). Caller role comes only from the independently authenticated bearer credential.

Worker calls permit `list_canvases`, `snapshot`, `health`, `ls`, `read`, `grep`, `resources`, `model_catalog`, `tasks`, `changes`, `end_turn`, `media_info`, `media_chunk`, and safe `apply` commands. Every batch is checked before dispatch; `upload_asset`, `export_output`, nested commands, and unknown command types are refused. `run_node`, `cancel_node`, `undo`, `redo`, `operations`, and all `timeline` operations are `worker_forbidden`. Fixed node-resource media reads intentionally extend the former Electron worker contract, which prohibited exports: workers can obtain local media files through these bounded selectors, not arbitrary URLs.

`run_node` for main requires `{nodeId,approval:{userApprovedNodeIds:[...]}}`, with the exact target in the nonempty string list. Optional `clearCandidates` (boolean; CLI `run --fresh`) discards the node's earlier candidates of the run's type before the result lands; by default a rerun appends to the node's candidate group (newest run becomes the primary; image and video candidates have no automatic eviction). Missing/invalid approval produces `approval_required` even on raw `/v1/call`. The browser strips this transport-only declaration after checking it and then invokes the existing run path. The declaration records the Agent's assertion of prior user authorization; there is no new UI confirmation token and it is not cryptographic evidence of user consent.

Worker files are independent private session records (`version:2`, `protocolVersion:2`, `role:"worker"`, `parentSessionId`) with separate CLI bearer tokens. The daemon never trusts a role edited into the local record. A worker cannot create/revoke other identities or stop the parent. Same-OS-user unrestricted shell access is outside this protocol boundary; a host requiring hostile-worker isolation must also hide parent credentials.

`requestId` is a UUID v4 permanently owned by its first authenticated caller session. The daemon fingerprints role, method, params (including approval), and turn ID. Only that caller may wait for or retrieve its result; parent/sibling lookups also fail with `request_id_conflict`. A duplicate with changed payload fails with the same code. Completed result cache is bounded to 256 entries/16 MiB. A mutation's request ID remains a tombstone for the life of the session when its result is evicted, returning `result_expired` without execution — that is the no-replay guarantee. Read IDs are retained only for the most recent 10,000, so a retried read past that horizon executes again (reads are idempotent). A daemon accepts at most 10,000 distinct MUTATIONS and 64 pending requests across all its callers.

All main/worker mutations serialize together; read operations can proceed beside them. Main timeline `list` is a read, other timeline operations are mutations. CLI default request timeout is 120 seconds. Unsent timeouts are `request_timeout` with `outcome:not_sent`. Connection loss after delivery is `unknown_outcome` with `outcome:unknown` and `requestId`; it revokes the browser connection and all delegates. No retries occur automatically. A late reply after connection shutdown cannot start later queued edits.

Revoking only one worker immediately disables its credential and removes its session file. Its unsent work returns `delegate_revoked`/`outcome:not_sent`; delivered work returns `unknown_outcome`. Delivered edits keep their serialization slot until the actual page reply or the original timeout. A late reply may then release the slot for the still-active parent, but never replaces the revoked caller's retained unknown result or replays its work. Main stop, page disconnect, and lease expiry revoke every worker. Revocation cannot claim to roll back work already sent to the browser.

## Account model catalog

The read-only `model_catalog` method accepts `{modelType?, modelId?, query?, offset?, limit?}`. It is available only through a paired page with an open canvas. The browser fetches the fixed same-origin `/api/gateway/models` route with its own session; no token, arbitrary URL, or custom header can be supplied by the CLI. Redirects are refused. The route is the human generation model picker's per-user catalog, containing only the intersection of authorized models and their published schemas.

The result is `{ok:true, source, models, total, offset, nextOffset}`. Each model contains `id`, `displayName`, `modelType` and `inputSchema` (or null with `schemaStatus:"missing"`). Full schemas are retained; pagination stops before the 512 KiB page budget rather than truncating a schema. The upstream response is bounded to 8 MiB/4096 entries and a 20-second fetch timeout. HTTP 401/403 becomes `unauthorized`; other HTTP/network failures become `model_catalog_unavailable`; malformed catalogs become `model_catalog_invalid`. The CLI command is `models`.

## Media

The standard upload is `apply` with a command:

```json
{
  "type": "upload_asset",
  "path": "reference.png",
  "fileName": "reference.png",
  "mimeType": "image/png",
  "bytesBase64": "...",
  "position": { "x": 100, "y": 200 }
}
```

The CLI enforces a 25 MiB input limit and workspace file boundaries. The existing page importer receives the bytes and goes through the normal asset import path.

`resources {nodeId,limit?,offset?}` reads the node-owned inventory without network I/O. It returns `{nodeId,resources:[{resourceId,nodeId,source,part,kind,current,available,name,fileName,mimeType,createdAt?,unavailableReason?}],nextOffset?}`. Source is `current`, `candidate`, `image-history`, `video-history`, `reference`, or `input`; `input` rows also have a `slot` (frame-first/frame-last/image/video/audio). Part is `media`, `poster`, or `last-frame`. URLs and text bodies are omitted. `limit` is 1–200 (default 100). Each request scans at most 2,000 source slots and returns an opaque `nextOffset` when more remain, including sparse pages. Reuse that offset rather than counting rows; restart paging if the node changes. IDs are node-bound fingerprints of source-entry identity and media part, stable across reordering. They are selectors, never authorization tokens. A missing or removed ID fails with `resource_not_found`. Unavailable legacy/local URLs are listed with `available:false`.

`media_info {nodeId,resourceId?,metadataOnly?}` resolves media only through an authorized node on the paired canvas. `resourceId` selects a resource previously returned by `resources`; omission keeps the current-output behavior. The same selector is supported by `apply` command `{type:"export_output",nodeId,path,resourceId?}`. Resolution checks the live node and accepts no arbitrary URL. It returns `{mediaId,size,mimeType,fileName,resourceId?}` for binary data or text larger than 8 MiB, and `{size,mimeType,fileName,content,resourceId?}` for smaller text. `size` is the exact byte length (UTF-8 for text), no greater than 256 MiB.

With `metadataOnly:true`, `media_info` returns `{size,mimeType,fileName,resourceId?,downloaded:false}` without downloading a body or returning text content. Binary `size` is `null` unless a completed download is already cached; text size is known. Metadata queries do not wait behind ongoing media downloads. Binary downloads reuse the same node/resource URL's cached bytes for ten minutes, at most 256 MiB and 256 entries per connection. The current node is resolved before every reuse. A different URL or expired cache downloads fresh bytes; disconnect clears the cache.

`media_chunk {mediaId,offset,length}` uses the opaque handle from `media_info`; length is at most 262144. It returns `{base64,offset,eof}`. Chunk offsets and bounds are validated. Binary handles are scoped to the browser connection and are never arbitrary URLs. The page may expire media handles; the CLI returns the failure and does not publish incomplete local output. Download targets stay inside the session workspace and use an atomic, no-clobber final publication unless overwrite was explicit.

Candidate resource rows include `outputId`. `apply` command `{type:"select_output",nodeId,outputId,expectOutputId?}` adopts only an existing generation candidate, via the native `selectGenCandidateOutput` and downstream `propagateOutputs` path in the batch's single Agent-owned Yjs transaction. `expectOutputId` is an optional compare-and-set precondition against the current adopted candidate (`null` means none). A mismatch returns `stale` with `currentOutputId`; a removed candidate returns `resource_not_found`. Both fail the entire batch without partial writes. Viewer and Agent undo boundaries are unchanged. A later human/remote whole-node write can supersede part of an undo step; inspect resulting node and downstream state rather than interpreting `undone` as a field-by-field guarantee.

## Host attestation (0.5, protocol 2)

`connect()` accepts `attest: (sessionId) => Promise<string>`. A signed-in desktop host uses it to fetch an opaque, session-bound token from the SceneMint server (`POST /api/canvas/agent-connect/attest`, authenticated with the user's EchoJoyAuth bearer). The daemon stores it as `hostAttestation` (printable ASCII, ≤ 4 KiB) and returns it verbatim in the `pair` and `resume` replies; CLI `status` only reports `hostAttested:true|false`. A failing callback means "no attestation" — the connection proceeds. The page hands the token to its own server (`POST /api/canvas/agent-connect/verify`) which decides: a valid attestation for the viewing user and this session ⇒ built-in Agent, always allowed; otherwise an external Agent, allowed only when the account holds the "any Agent" entitlement. The page disconnects with `entitlement_required` / `entitlement_expired` on a refusal; the daemon never sees the verdict. The attestation expires after ten minutes but the daemon session may live for hours and re-verifies on every resume, so the server remembers a built-in verdict per (user, session) for 24 hours (`agent_connect_sessions`) and consults it before the attestation's own expiry. A verify call that cannot be completed (network, 5xx) is retried by the page — three times on pair, with the reconnect backoff on resume — and is never a verdict.

**Boundary, stated plainly:** the attest endpoint only checks that the bearer is an active EchoJoyAuth user. Any local process holding that user's access token (for example one that read `~/.config/ly/config.json` after `ly auth login`) can mint an attestation for its own daemon session and appear built-in. Closing that requires the auth service to issue desktop-client tokens with a distinguishing claim (or a device credential kept in the client keychain) and the attest endpoint to demand it. Until then this gate separates product tiers for ordinary customers; it is not a defence against software running as the same OS user.

## Batch run (0.6, protocol 2)

`run_nodes {nodeIds?,groupId?,rerunSucceeded?,clearCandidates?,concurrency?,approval:{userApprovedNodeIds}}` is a main-only mutation (`clearCandidates` as in `run_node`, applied to every node of the batch) (workers get `worker_forbidden`). The daemon validates the shape, `concurrency` 1–200 (default 24; the page spaces submissions ~250 ms apart for the gateway's per-user 5/s limit) and that every `nodeIds` entry is in `approval.userApprovedNodeIds`; a `groupId` is expanded by the page, which re-checks the full expanded list and refuses the whole batch with `approval_required` if any member is missing. The page runs the same executor as its own "run selected / run group" (topological order by reference edges, concurrency cap, downstream waits for upstream `succeeded`). `concurrency` is this batch's own cap; across ALL batches on the page — the user's own "run selected" batches included — at most 200 nodes are in flight at once for the account. Batches never reject each other: a node over that ceiling simply waits in its batch's queue (it is neither `pending` in the reply's sense nor `skipped`) and is submitted as soon as a slot frees. The reply arrives once the first wave has been accepted: `{ok,order,submitted:[{nodeId,taskId?}],pending:[…],skipped:[{nodeId,reason}]}`; the batch keeps running on the page. Skip reasons: `not_found`, `not_runnable`, `running`, `succeeded`, `upstream_not_ready`, `upstream_failed`, `cycle`, `cancelled`, `submit_timeout`, `claimed` (already waiting in another batch on this page — never double-submitted). A node that stays `running` beyond the run limit (image 10 min, video 30 min, text 5 min) releases its slot as `failed` with message `run_timeout`; the cloud task is untouched and the page writes a `changes` entry `{kind:"batch", note:"run_timeout", nodeIds:[…]}`. Every submitted node is a chargeable attempt against the account's generation balance, so the first failure classified `quota` aborts the rest of that batch: the page drops the not-yet-submitted nodes (`skipped` reason `cancelled`), leaves already-submitted ones running, and writes `{kind:"batch", note:"quota_stop", nodeId:<the node that hit quota>, nodeIds:[…the dropped, never-submitted ones]}`. The node that failed is the entry's `nodeId`, not a member of `nodeIds`: which of them already reached the gateway must be readable by name, because a positional rule gets re-encoded downstream and a later reorder would silently invert it. Whether that submission was actually charged is settled gateway-side and is not observable here. Stop and tell the user; do not resubmit the batch. A batch lives only in the page: after a reload the replacement page reports the nodes the previous page never submitted as a `changes` entry `{kind:"batch", note:"batch_lost", nodeIds:[…]}`, sends `lostBatch:{count,nodeIds}` in its `/v1/resume` body, and CLI `status` shows `lostBatch` until the next resume. Nothing is replayed. A node whose submit the server had already accepted is NOT in that list even if the reload hit before the gateway id came back: the page binds the accepted row to the node the moment the enqueue is acknowledged, the node comes back `running`, and the result lands on it through resume — so `batch_lost` really does mean "nothing was paid".

`run_nodes` replies with `batchId`. `cancel_batch {batchId?}` (main-only mutation) drops the nodes of that batch that were never submitted — all of the caller's batches when `batchId` is omitted — and answers `{ok,cancelled:[…],batches:[…]}`; submitted nodes keep running and are cancelled per node. `cancel_node` on a node still queued in one of the caller's batches drops it from the queue instead of answering `not_owned`. The first `run_nodes` reply comes back as soon as the first submission has an outcome (or after 2 s); the batch continues on the page and is listed in the page's batch panel, where a human can cancel the unsubmitted remainder too. Submissions of every kind (human or Agent, single or batch) pass a page-level token bucket of one request per 250 ms right before the HTTP call, so the gateway sees at most 4 submissions per second per page.

## Generation tasks (0.8.1, protocol 2)

Every generation submit the page makes records who asked for it: `client.submitter` on the media task row is `{kind:"human"}` for a run started on the page and `{kind:"agent",sessionId,name}` for a run the bridge started, where `sessionId` is the connection's registered Agent identity (`scenemint-cli:<main session UUID>`, shared by its workers). The read-only `tasks` method — `{scope?,nodeIds?,status?,submitter?,since?,limit?,after?}`, workers included — is served by the page from the same server feed the task centre reads (the signed-in user's own media tasks in spaces the user can see; the CLI never receives a cookie or URL) and answers `{ok,canvasId,scope,rows:[{taskId,mediaTaskId,nodeId,nodeTitle?,kind,status,submittedAt,startedAt?,finishedAt?,submitter:{kind,sessionId?,name?,isMe},error?,batchId?,canvasId?,canvasName?,projectId?,projectName?}],nextAfter?,scopeNote?}`, newest first. `status` is `queued` / `running` / `succeeded` / `failed` / `cancelled`; `submitter.kind` is `human`, `agent` or `unknown` (rows written before this field existed are reported as unknown, never guessed); `isMe` is `submitter.sessionId === <this connection's identity>`. `submitter:"me"` narrows to that identity; `nodeIds` (1–200) filters page-side; `limit` is 1–500 (default 100); `after` is the previous reply's `nextAfter`. `scope` is `canvas` (default — the paired canvas), `project` (every canvas in its space) or `all` (every visible space); rows outside the paired canvas carry `canvasId`/`canvasName`/`projectId`/`projectName`, the reply carries the fixed `scopeNote` "只读：这些任务属于其它画布/项目，Agent 不能在那里操作，只能报告状态", and those node ids remain inert for every other method — the bridge is bound to the paired canvas and `read` / `run_node` / `cancel_node` on them fail exactly as for any unknown node. `ls --long` rows and `read` nodes additionally carry `run:{taskId?,submitter?:{kind,isMe},submittedAt?}` for a running or last-run node, from the node's binding plus a tasks-feed cache the page refreshes at most once per call (~5 s); the page fills `agentId` into those reads itself. `cancel_node` answering `not_owned` is the same fact as `submitter.isMe:false` on that node's task.

## What changed in 0.10.1 (upgrading from 0.10.0)

`protocolVersion` stays **2**, `bridgeVersion` stays **3**, the 20 apply commands and their fields are untouched. One reply field is added.

`apply` replies now carry **`focused[]`** — `{command, nodeId, framed, reason?}`, one entry per `focus_node` in the batch, present whenever the batch held one (including, above all, when nothing was framed). `focus_node` is the single command whose effect is not in the document: it moves a camera in one browser, and the transaction it rides along with commits either way. When the page had not measured that node's geometry the framing simply did not happen and the reply said **nothing at all** — `ok:true`, no field — so the only thing a caller could report was "the user is now looking at it" about a screen that never moved. `framed` is the proof; the batch's `ok` is not.

`reason` appears only on `framed:false` and its two values need different answers to the user: `unmeasured` — this page has a camera but no geometry for that node yet (off-screen in a virtualised canvas, or created in this same batch), so a later attempt can succeed; `no_camera` — this host embedded the bridge with no camera wired (`fitNodes`), so no `focus_node` will ever work in it and the honest reply is to name the node instead of promising a view change. The closed set is published as `CANVAS_CONTRACT.focus.unframedReasons`.

A downstream that ignores the field keeps the old behaviour, minus the ability to tell the two silent failures from success — which is the whole point of the release.

## Group frames and canvas tidy (0.9 / 0.10, protocol 2)

Nothing on the wire changes: `resize_group` and the `tidy` scope fields are `apply` command payloads, checked by the same `COMMAND_FIELDS` table the daemon already enforces, and `protocolVersion` stays 2. What 0.9 adds for an integrator is in `./contract`: `limits["group_nodes.minMembers"]` (**1** — the page accepts a one-member group, and a product that still self-censors at 2 silently drops those groups) and `limits["group.oversizeRatio"]` (**3** — a frame counts as oversized when its area exceeds its members' bounding box by this factor; a product that shrinks at its own ratio eats the whitespace a user left on purpose). Both are bare numbers, not `{min,max}` objects, because consumers read them with `Number(v)`. The same module exports `PAGE_AWAY`, the field names, error code, `outcome` values and exit code of the path described under **Reconnect** below — the strings were being copied by hand into four trees, where a rename reads as "the page is fine" rather than as a failure.

**Added in 0.10.** Membership under a frame gesture, both halves of it. A frame gesture — a human dragging the frame, a human pulling one of its eight grips, or `resize_group` — commits geometry and changes **no** membership: a node the frame now covers does not join, and a member the frame no longer covers is not evicted. Two things follow for an integrator.

_It is reported._ When a human's frame gesture leaves the canvas in that mismatched state, the page writes `changes` entries `{kind:"batch", note:"frame_strays", actor:"human", nodeId:<the frame>, nodeIds:[…the covered non-members]}` and `{kind:"batch", note:"frame_escaped", …the members now outside}`. They carry `actor:"human"` rather than `"page"` — a human's hand produced the fact, and `actor` is what a product branches on to decide whether to say "you changed this". Stray and escaped are two entries, never one mixed `nodeIds` array: the repairs are opposite. Both are records; nothing on the canvas changed.

_One criterion._ A node is a **stray** of a frame when its **centre lies inside that frame** — that single test is what `health`'s `stray_over_frame` reports, what `tidy` returns in `strays[]`, what the `frame_strays` change entry lists and what `absorbStrays` takes in. A node that only clips a frame's edge (centre outside) is not a stray anywhere: it is a plain overlap, and `tidy --scope all` pushes it off the frame. The two criteria used to disagree — health judged rectangle intersection, everything else judged the centre — so a node with 30 px inside a frame was reported and then could not be repaired by the very command the report prescribed.

_It is repairable (0.10)._ `resize_group` takes `absorbStrays` (boolean, default false, in `COMMAND_FIELDS.resize_group`): **before** the resize, every node whose centre falls inside the frame as the command found it **and that has no parent at all** joins the group, and the reply carries `absorbed:[{command,nodeId,nodeIds}]` naming them. The new size is then computed over the new member list, so `fit:true` ends up covering the nodes it just absorbed, and a `size` too small for them is held at the members' floor. (Absorbing after the resize was a no-op: `fit` pulls the frame in to the members' bounding box, which by definition excludes strays.) A node owned by another group is never taken, however far the frames overlap. There is no inverse switch — nothing evicts a member — because a frame is also a deletion unit (`delete_node <group>` takes its members), so joining is the direction that has to be asked for and leaving is the direction that must never happen by accident. CLI: `resize-group <group-id> --fit|--size WxH [--absorb-strays]`.

## Canvas health (0.10, protocol 2)

`health {maxIssues?, groupMinMembers?}` is a new read method — read-only, idempotent, worker-allowed, no undo step — that answers "what is wrong with this canvas right now" as a table of violations instead of as geometry the caller has to reduce itself. Every input it needs was already on the wire (`snapshot` gives each node a `position`, a `size` and a `parentId`, and each group row a `bounds`, `memberIds`, `membersBounds` and `frameOversize`), and that is exactly the problem this method exists for: reducing a few hundred of those rows to a conclusion means rectangle containment, intersection and area ratios over coordinates that are **parent-relative for grouped members**, and the models that drive these sessions get it wrong in a specific, reproducible way — they treat a member's stored position as absolute and report escapes that are not there.

The judging happens **in the page**, over the whole graph. This is not an optimisation: `snapshot` clamps at 2000 nodes (`HARD_MAX_NODES`), so a 2400-node canvas cannot be health-checked through it at all, and a conclusion drawn over half a canvas is worse than no conclusion — the shipped layout report read a clamped reply as "this is clean". So `scanned:{nodes,groups,edges}` reports what was actually examined and is never clamped, `counts` is always the complete per-kind tally, and `truncated:true` / `omittedIssues:N` can only ever mean "the `issues[]` **detail list** was cut", never "the canvas was not fully seen".

The reply is `{canvasId, rev, seq, scanned, counts, totalIssues, issues[], truncated?, omittedIssues?, healthy}`. Each issue is `{kind, nodeId?, groupId?, otherId?, message, metrics?, fix?}`: `message` is one plain sentence naming both parties, `metrics` holds the numbers that sentence quotes (overflow pixels per side, area ratio, intersection area), and `fix` is an argv a caller can run verbatim. `./contract` publishes `health.issueKinds` — `dangling_mention`, `member_escaped`, `group_frame_oversize`, `stray_over_frame`, `group_overlap`, `node_overlap`, `group_empty`, `group_undersized`, in that order, which is the severity order the detail list is sorted by so a clamp keeps the worst — plus `limits["health.maxIssues"]` (1–1000, default 100) and `limits["health.overlapMinRatio"]` (**0.02** — two nodes count as stacked only when the intersection covers this fraction of the smaller one's area; a bare pixel constant is wrong on a canvas that holds both 498×280 gen nodes and 4000 px stills). Branch on `kind`, never on `message`. One `fix` changes membership — `resize-group <group> --fit --absorb-strays` for `stray_over_frame` — and a frame is also the deletion unit, so that one needs the user's word before it runs; `dangling_mention`, `group_empty` and `group_undersized` carry no `fix` at all, because only a human can decide what the right content is.

Cost: one shared id index for the whole scan (the same rule `snapshot`'s projection follows) and spatial bucketing for every pairwise test, so a **healthy** 2000-node / 200-group canvas is tens of milliseconds on the page's main thread rather than the four million comparisons a naive double loop would do.

That figure only describes the shape where nothing overlaps, and `health` is called precisely when the canvas looks like a mess. The number of violations is itself O(intersecting pairs), which is O(n²) once nodes are stacked — a copy-paste or a bulk import leaves 2000 nodes at one point, and that is 1,999,000 `node_overlap` rows. So the per-kind cap is applied **while violations are produced**, not after: once a kind has `maxIssues` detail rows the rest are counted and nothing further is materialised, and an issue's `message` is formatted only for the rows that actually go into `issues[]`. The same 2000 stacked nodes measured 2.5 s of synchronous main-thread work before that (two million objects on the heap, every Chinese sentence formatted, sorted, then 100 kept) and ~150 ms after — roughly the floor for merely counting that many pairs. `counts` stays the complete tally either way; what a caller loses is only detail rows it never asked for, and `truncated` / `omittedIssues` say so. The CLI's text report additionally states the omitted count **per kind**, because the top-level `omittedIssues` is a single total and cannot tell a caller that one kind alone has half a million rows.

## Freshness and tidy reporting (0.10, protocol 2)

One `changes` row can stand for many nodes: a single transaction that touches more than one node from the page's own automatic writer (`actor:"page"` — the frame that refits itself around its members), or **eight or more** nodes from anyone else, is merged into `note:"bulk_change"` rows rather than one row per node. `nodeIds` is what the row covers and there are no `fields`; re-read what you care about. The same merge applies to EDGES on the same width rule, and it has to: nodes and edges are two separate maps reported by two separate calls, so deleting a group of wired nodes used to collapse the node side into one row and then flood the buffer with one row per edge from that same transaction. The merged edges row is the one exception to "read the id list": there is no `edgeIds` field in this contract and edge ids are only ever obtainable from `snapshot` anyway, so it carries `fields:["edges"]` as its subject and no ids at all — `{kind:"delete", note:"bulk_change", fields:["edges"]}` means "one transaction removed a batch of edges, re-read the wiring you care about". A refit moves ten members plus the frame in one write, so at one row per node twenty landed images from a collaborator filled 200+ of the 500-row buffer with the page's own housekeeping and evicted the human edits.

**Merging never crosses an action.** One wide transaction yields at most three rows — `{kind:"add", note:"bulk_change", nodeIds}`, `{kind:"delete", …}` and `{kind:"batch", …}` for the move/update noise — so deleting a 200-node selection is still one row, but it is a `delete` row naming all 200, not an undifferentiated `batch`. Branching on `kind` therefore stays correct at any width; a single-node action inside a wide transaction keeps its plain `nodeId` row, and a lone edge keeps its plain `edgeId` row (a lone move/update keeps its `fields` too — merging only ever drops the per-key detail of a bucket that actually has several keys). A `nodeId` is absent exactly when `note:"bulk_change"` is present, so read `nodeIds` whenever `note` is set rather than branching on `kind` for it — except on the edges row, which has neither (`fields:["edges"]` is how you recognise it). `actor` is whoever ran it and **may be `human`**: a human's own multi-select delete or drag is exactly the case this merges. The `doc-index` delete is never merged into any of these rows.

Two counters travel with canvas replies and they are **not** comparable. `rev` is the document revision: it ticks on every document transaction — nodes, edges, docIndex **and `meta`, which is the saved viewport and the video timeline** — the caller's own writes included, and it is what answers "is the thing I read still current". A human panning or zooming therefore moves `rev`: the page rewrites the saved viewport ~400 ms after the gesture, and that write deliberately produces no `changes` entry (one drag would push a dozen and evict real edits at the 500-entry cap), so a moved `rev` is its only trace. A moved `rev` consequently means "something here may have moved", never "re-pull the whole snapshot" — re-reading 2000 nodes because the user scrolled is the mistake this sentence exists to prevent. Follow it with `changes {sinceSeq, sinceEpoch}`: entries name what to re-read, and `entries:[]` with no `truncated` means the document itself did not change (only the camera, or your own writes, which never produce entries). `seq` is the change feed's cursor: it counts only what this agent did **not** do (human, remote peer, and the page's own housekeeping), and it is what `changes {sinceSeq, sinceEpoch}` resumes from. Never compare one against the other, and never conclude from an unchanged `seq` that the document did not change — your own `apply` leaves `seq` untouched by design.

**A `seq` is only half a cursor.** The feed is a module singleton inside the page, so a reload rebuilds it at 0, and `seq` then counts again over history the caller has never seen. The old guard for that was `sinceSeq > seq`, which only holds while the rebuilt feed is still shorter than the remembered number: remember 57, let the user reload and make 80 more edits, and `changes {sinceSeq:57}` answers `{seq:80, entries:[58..80]}` with no `truncated` — a gap-free-looking delta of "23 things happened" that hides the 57 real edits entries `1..57` describe. So `changes` and `snapshot` both return `epoch`, a fresh random id per feed instance, and a caller resuming a cursor sends the pair back as `{sinceSeq, sinceEpoch}` (CLI: `--since-seq N --since-epoch E`). A mismatch is `feed_restarted` whatever the numbers say, and **a non-zero `sinceSeq` with no `sinceEpoch` is `feed_restarted` too** — the page cannot prove the number belongs to it, and the recovery (re-snapshot, continue from that reply's `seq` and `epoch`) costs one call. A remount or client-side navigation does **not** change the epoch: the feed object survives those and its count really did continue.

`snapshot` now returns `rev` and `epoch` alongside `seq`, so "snapshot → work → snapshot" can prove freshness with one call, and "re-snapshot, then resume the feed" is a loop that closes. Before this, `rev` appeared only on `ls` / `read` / `grep` / `apply` and `snapshot` carried `seq` alone, so no single reply gave both and a snapshot could not be checked against the apply that followed it.

`apply.tidied[]` now carries an entry for **every** `tidy` command in the batch, `{command,moved,resized,strays[]}`. Previously only the `scope` form reported, and the whole-canvas re-layout answered with nothing at all — a caller could re-lay a user's entire canvas and read back only "applied 1 command". `moved` / `resized` count what actually changed on screen (a node already in place is not counted). `strays[]` is the conservative `scope` pass naming the nodes it **refused** to move — escaped from or overlapping a frame — and is the only channel that says "something here needs a human"; the re-layout refuses nothing, so its `strays` is always `[]`. The **page** renders the same facts as `tidySummary`, one text line per entry with the strays named, and it travels with `tidied[]` on **both** paths a tidy arrives by — a plain `apply` batch containing a `tidy` command, and the CLI's `tidy`. That matters because the JSON never reaches the model: a host compresses the reply into "applied 1 command", which carries neither the counts nor the stray ids. The renderer is published as `formatTidySummary` on the `./contract` subpath, so a host pastes one string rather than re-deriving the wording; the CLI only computes it as a fallback for a page too old to send one.

## Reconnect (0.5, protocol 2)

A successful pair adds `resumeSupported:true`, `resumeMs` (the daemon's recovery window, default ten minutes) and `pageEpoch:1`. The session state machine is `awaiting_pair → connected ⇄ reconnecting → disconnected`. The daemon enters `reconnecting` on its own when the browser lease lapses (45 seconds without contact) or when the page sends `POST /v1/suspend {}`; either way it keeps main/worker credentials, request-ID tombstones and **undelivered** queued calls for `resumeMs`. Calls issued while `reconnecting` are accepted and queued, not refused; a queued call has no clock while the page is away (its `callTimeoutMs` clock starts when the page is connected and restarts at delivery) and fails as `not_sent` only on that clock or on final disconnect. A delivered mutation that is retired at suspend keeps the serialization slot until its own clock, a late reply, or a replacement page's resume — a throttled tab that merely missed the lease is still executing it. Delivered-but-unanswered requests can never be answered by a replacement page: they are retired as `unknown_outcome` at suspend/resume time and are never replayed. A delivered request that times out is likewise retired on its own, without ending the session.

`POST /v1/resume {protocolVersion:2,canvasId,projectId}` requires the current browser credential and exact project/canvas. It is accepted in `connected` (a page that lost its poll while the lease was still live) and in `reconnecting`. A successful resume rotates the browser token, returns the normal pair fields plus `resumeSupported:true`, `resumeMs`, incremented `pageEpoch` and `undoHistoryReset:true`, and delivers the queued calls to the new page. Requests carrying the old token are rejected with `unauthorized`, except for the bounded, exact-operation retry described below; a page receiving a terminal refusal to `resume` gives up. An outstanding `next` poll is answered `{suspended:true}` when the daemon parks the session or another page instance resumes it; the page then tries `resume` itself. Explicitly disconnected or expired sessions cannot resume.

**Response-loss recovery (optional protocol-2 capability).** New pair/resume replies advertise `resumeIdempotent:true`. Before sending a resume to such a daemon, the page durably writes a fresh UUID `resumeRequestId` alongside the current browser credential in its tab checkpoint, then includes that ID in the resume body. A retry, including one from the replacement document after a hard reload, uses that same ID and credential. The daemon retains only the latest unacknowledged rotation for at most `resumeMs`: the old credential is accepted solely for `/v1/resume` with that exact ID and original origin/protocol/project/canvas. It returns the identical credential and epoch, without rotating again or replaying work. Wrong IDs, other routes, expired records and disconnected sessions are rejected. A valid `/v1/next` using the new credential acknowledges the handoff and invalidates the old-credential retry; a subsequent rotation supersedes the previous record too.

The page saves a received new credential immediately, before `/verify`, and clears the pending operation ID atomically with that save. Authorization still must succeed before registering an Agent or polling for work. `pagehide` stops local polling/recovery and suspends the session; retained-document `pageshow` restores from the latest checkpoint. Nothing disconnects on `beforeunload`, so cancelling a leave prompt keeps the original connection. Responses arriving after local teardown cannot overwrite the replacement checkpoint. Legacy daemons without the capability retain the original resume format and do not gain the response-loss guarantee; update the CLI and start a new session to enable it.

CLI status includes `pageEpoch` and, while suspended, `resumeExpiresAt`. A page epoch change requires rereading canvas state and restarting changes cursors/media handles. The daemon retains request ID ownership, caches and tombstones; the recreated page cannot restore its Yjs undo stack, so status reports `undoHistoryReset`. Closing a tab never creates a background executor.

**The caller is never left on a silent socket (protocol 2, `page_away`).** A call whose page is away — issued in `reconnecting`, or queued while `connected` and then stranded by a lease lapse — is answered `{ok:false,error:{code:"page_away",retryable:true,queued,outcome,state,resumeExpiresAt,pageLastSeenAt,pending,requestId?}}` instead of waiting out the recovery window. A **read** is never queued: after 5 s (`PAGE_AWAY_READ_MS`) its record is dropped, `queued:false`, `outcome:"not_sent"`, nothing happened. A **mutation** stays queued with its id, fingerprint and tombstone — the page executes it exactly once when it resumes — and the caller is told `queued:true`, `outcome:"queued"`, `requestId` after `waitMs` (body field; CLI `--wait-ms`, default 30 000, at most `resumeMs`); it collects the result later by re-issuing the same id (`--request-id`), which attaches to the queued record or returns the cached result. `wait:true` (CLI `--wait`) restores the blocking form for the whole window. `wait`/`waitMs` are transport hints, not part of the request fingerprint. `status` carries `pageAway` (= `reconnecting`), `queuedCommands` (undelivered), `pageLastSeenAt` (last browser contact, ISO, `null` before pairing) and `daemonPid`. An outstanding `next` poll counts as browser contact for the lease: it is the page's own open socket.

**What resume cannot do.** The checkpoint is tab-scoped `sessionStorage`: a reload, navigation or bfcache restore of the _same tab_ resumes; a new tab, a restarted browser, or a desktop host that recreated its webview has no checkpoint and cannot resume — the host must pair again. CLI `connect --session ID` is the one call for that: it reuses the session when its daemon process is alive and its page is `connected` or `reconnecting` with `pageLastSeenAt` within 60 s (reply `reused:true`, no new code), and otherwise stops/unlinks the stale session and mints a new one (`reused:false`, `replaced:{sessionId,reason}` with `daemon_exited` / `page_away_too_long` / `awaiting_pair` / `disconnected` / …). A host that keeps its own session file must never treat that file as proof of life; `status` (or `connect --session`) is.

`read` now includes `mentionCandidates:[{key,label,syntax}]` for usable target references. `syntax` is the exact readable token accepted by the bridge; `mentions` remains the list actually bound in the stored prompt.

## Single invitation and multiple page connections (0.4, protocol 2)

CLI connect adds `connectionCode = SM1.<port>.<one-use random token>`. This is packaging, not encryption; the browser parser accepts only a valid loopback port and a 43-character base64url token. Origin binding, ten-minute expiry and atomic one-use pairing remain daemon checks. Legacy endpoint/pairCode fields remain for protocol compatibility. Each daemon still binds exactly one canvas. The page owns a collection of independently authenticated connections, identities and refresh checkpoints keyed by endpoint. Disconnecting one removes only its checkpoint and authority.

## Library subpaths are an implementation, not this contract

`package.json` exports `./client`, `./session`, `./media` and `./common` in addition to the supported `./policy` and `./contract`. They exist for a product that carries its own canvas business layer and wants to reuse this connection layer from an installed package instead of copying `src/*.mjs` into its own tree. `connect`/`call`/`sessionRequest` speak exactly the routes above; `readSession` reads the credential file described under **CLI routes**; the media helpers are the chunked-transfer client for `media_info`/`media_chunk`.

What is normative is this document and the CLI's JSON output. Those four modules are one implementation of it, exported for convenience, and are explicitly **not** a stable API: their export names, signatures and return shapes may change in any release, they carry no `.d.mts` declarations, and no compatibility guarantee is made across versions. A consumer that needs stability pins an exact version, asserts the behavior it relies on in its own tests, and treats the wire protocol — not the module surface — as the thing it integrated against. Adding a route, an error code or a field here is a protocol change and is described above; renaming an internal helper is not.

How the code reaches the page is outside this protocol: a human pastes it, or a desktop host that owns both ends hands it to its own webview through the page's pairing entry (`window.__sceneMintAgentPairing.pair({code,canvasId?})`, documented in `docs/integrations/agent-bridge.md`). Neither route changes a byte on the wire, and neither skips a check: the same parser, the same one-use `/v1/pair`, and the same `/api/canvas/agent-connect/verify` verdict decide in both. The entry answers `{ok:true,canvasId,projectId,agentId,agentName}` or `{ok:false,error:{code,message,reason?}}`, where `code` is `invalid_code`, `duplicate`, `canvas_not_found` or `connection_failed` and `reason` carries the daemon/authorization code behind the last one.
